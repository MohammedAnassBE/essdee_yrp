Overview

Merch owns the style and order data that every other department consumes: the lot, the Item Production Detail (IPD), the PPO approval, process work orders and their rates. Today that work happens in Desk or inside the Purchase and Sales pages. This plan gives Merch one /web department with the same look as Cutting.

Goal

Merch users do lot and IPD entry in /web, faster than the old production_api IPD form. Every page is permission-driven: the server says what the user can read, edit, submit or approve.

Who uses it

  • Merchandiser / Merch User: lots, IPD entry, work orders, process cost drafts.
  • Merch Manager / Senior Merch: IPD approval, PPO approve or request changes.
  • Purchase: keeps its own read-only lot view. Purchase pages are not changed.

The eight cards

  • Lot · Item Production Detail · Production Order · Work Order
  • Process Cost · Vendor Bill Tracking · Purchase Invoice · Reports

The voice note said five cards and listed six. Bill Tracking and Purchase Invoice were added later, so the plan shows eight. See open questions.

Action buttons: who sees what

One rule for every Merch screen: a button appears only for users whose role is allowed to perform that action, and the server checks the role again when the action runs. If a settings field names the role, the role is read from that field. If no settings field exists, the tables below say so, and today's gate stays as it is (DocType permission, a Workflow role or a hard-coded role). This plan adds no new settings.

Path prefixes used below: E/ = apps/essdee_yrp/essdee_yrp/, Y/ = apps/yrp/yrp/, F/ = apps/essdee_yrp/frontend/src/. Line numbers point at the def or the field and were checked on 2026-10-15.

The pattern, as the Production Order already does it

Four steps

  1. Read the role from settings. get_ppo_approver_roles() (E/production_order_workflow.py:856) reads merch_user_role and merchandising_manager_role (PPO_APPROVER_ROLE_FIELDS, :43) with frappe.db.get_single_value("SD YRP MRP Settings", …). onload() (:154) turns it into flags such as can_approve_ppo.
  2. Compute {allowed, label, reason} per action. _production_order_actions() (E/sales/web_workspace.py:244) combines docstatus, status, DocType permission and the role flags. get_production_order_workspace() (:327) returns the result as capabilities. The shared helper is web_common.action() (E/web_common.py:38).
  3. Render only allowed actions. The page maps capabilities to DocumentActionStrip buttons and drops allowed: false (F/departments/sales/ProductionOrder.vue:87). Bill Tracking and Purchase Invoice already do the same.
  4. Re-check on execute. execute_production_order_command() (E/sales/web_workspace.py:496) rebuilds the same capabilities and throws PermissionError when the action is not allowed (:507-514). The domain function then checks the role again, for example approve_ppo() (E/production_order_workflow.py:1033).

Merch rules

  • An action the user's role does not allow is hidden, not shown disabled.
  • A disabled button with a reason is only for a user who holds the role but has to fix the document first (for example an IPD approver while checks still fail). DocumentActionStrip already supports disabledReason (F/components/documents/DocumentActionStrip.vue:107).
  • Every new Merch execute_<doc>_command follows step 4: rebuild the capabilities, refuse if not allowed, then call the domain function. The role is defined in one place, the settings field.
  • If the settings field is empty, the button is hidden. The domain function throws a "configure … in MRP Settings" error, as require_ppo_action_role() does today (:878). System Manager passes only where the existing code already lets it.

Item Production Detail Phase 1

The main piece of work, and it is built first. Phase 1 matches the current doctype field for field (see the field map below). Changes come later from the user, one at a time, and go into the change log. Today the IPD is a Desk form (essdee_yrp/public/js/item_production_detail.js, 1,856 lines) on YRP Item Production Detail with 120 essdee custom fields, eight tabs, nine "Get … Combination" buttons and about thirteen embedded Vue widgets. There is no IPD page in /web yet: IPD links resolve to /web/document-unavailable.

What the new entry flow changes

One page, nine sections

A single scrolling editor with a section index on the left. Sections are a real order of work, so they are numbered. Each shows done, needs attention or not started.

Grids instead of widgets

Every repeated value (packing quantities, stitching panels, cloth mapping, consumption) is a keyboard grid: type, Tab, Enter, paste a block from Excel, fill right, fill down, apply to all colours.

Checks while typing

A checks panel runs the same server rules as save (ipd_validations.validate) on the draft and lists every problem with a jump link, instead of failing one at a time on the second save.
